# Suppress Warnings Unless Verbose PRD

## Introduction / Overview
The current CLI sometimes emits warning output generated by the tool itself or its third-party dependencies (e.g., `yt_dlp`, `youtube_transcript_api`). This noise makes the default transcript output harder to script against or paste elsewhere. We want the CLI to run silently by default, only surfacing those warnings when a user explicitly requests them via a `--verbose` flag. README documentation should note this new flag along with an example.

## Goals
- Default transcript runs produce no warning output.
- Introducing a `--verbose` CLI flag restores the current warning behavior when requested.
- Warnings can be surfaced even when `--json` output is enabled.
- README documents the `--verbose` flag with usage guidance and an example.

## User Stories
- As a user piping transcript output into another script, I want the default run to omit warning noise so my automation consumes only transcript text.
- As a power user troubleshooting a failure, I want to re-enable warnings with `--verbose` so I can see diagnostic information without modifying source code.

## Functional Requirements
1. The CLI must accept a `--verbose` flag in addition to existing arguments.
2. When `--verbose` is absent, suppress warning output originating from the tool or bundled dependencies (e.g., Python `warnings`, library logging, or other stderr messages considered warnings).
3. When `--verbose` is present, emit warnings using the same destination and format as the current implementation (no regression in warning content).
4. `--verbose` must be compatible with the `--json` option so that JSON output still prints to `stdout` while warnings appear in their usual stream (likely `stderr`).
5. README must describe the new `--verbose` flag, including a short example demonstrating default vs. verbose behavior.

## Non-Goals (Out of Scope)
- Adding new diagnostic logging beyond existing warning output.
- Refactoring broader CLI argument parsing unrelated to the `--verbose` flag.
- Changing the structure or fields of the JSON payload emitted with `--json`.

## Design Considerations (Optional)
- Decide whether to introduce `argparse` (or similar) to simplify flag handling versus continuing manual argument parsing.
- Centralize warning suppression so it covers the tool's own warnings and those from third-party dependencies without muting actual errors.

## Technical Considerations (Optional)
- Python's `warnings` module can globally filter warning categories; third-party logging may require configuring logging levels or handlers.
- `yt_dlp` offers quiet/silent options; confirm whether additional flags or logger configuration are needed to suppress its warnings when not verbose.
- Ensure suppression does not swallow fatal errors that should still terminate the script.

## Success Metrics
- Running `python main.py <url>` with valid input produces transcript output only, no warning text.
- Running the same command with `--verbose` reproduces existing warning messages (e.g., network fallback notices).
- README contains a documented `--verbose` section with an example invocation and expected output description.

## Open Questions
- Are there specific warning classes or loggers that should remain visible even without `--verbose` (e.g., deprecations the user must address)?
- Should we add automated tests (unit or integration) verifying warning suppression behavior?
